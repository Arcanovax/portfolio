## Description

This project implements an autonomous coding agent that uses <span style="color: #22a3ff">Large Language Models (LLMs)</span> to solve programming problems and fix bugs in real-world software repositories.

Instead of generating code as a final answer, the agent follows an iterative execution loop: it generates Python code, executes it in a sandbox, observes the output, and uses the results to decide what to do next.

The project supports two distinct workloads:

- **MBPP (Mostly Basic Python Problems)**: Generates Python functions and validates them against predefined assertions.
- **SWE-bench**: Explores existing repositories, investigates reported bugs, edits source files, runs tests, and produces a Git patch.

The system combines an LLM abstraction layer, a restricted code-execution sandbox, and benchmark-specific tools exposed through the Model Context Protocol (MCP).

The main technical objective is to move beyond static code generation and build an agent capable of iterative reasoning, tool usage, execution, debugging, and objectively evaluated problem solving.

## System Architecture

1. **Agent Loop**: Maintains the interaction between the LLM and the execution environment. Each iteration generates executable Python code, runs it, captures the output, and feeds the resulting observations back into the model. The agent stops when it reaches a final answer or an execution limit.

2. **LLM Integration**: Communicates with OpenAI-compatible model providers through a configurable interface. Supports model selection, API-key rotation when rate limits are encountered, and tracking of token usage, latency, and retries.

3. **Sandbox**: Executes model-generated Python in a fresh child process. It inspects source code before execution, restricts imports and built-ins, confines filesystem access, disables network access, applies resource limits, and enforces a wall-clock timeout.

4. **MCP Tool Servers**: Expose benchmark-specific operations through the Model Context Protocol. The sandbox discovers the available tools and makes them callable from generated Python code. This separates the agent's execution interface from the implementation of individual tools.

5. **MBPP Agent**: Receives a programming problem, generates a candidate solution, executes it against assertions, and submits the result in the expected evaluation format.

6. **SWE-bench Agent**: Operates on a real software repository within a Docker-based task environment. It explores the codebase, modifies files, runs project tests, and generates a patch intended to resolve the reported issue.

7. **Evaluation Pipeline**: Saves each run to a structured JSON artifact containing the proposed answer and per-iteration metrics. A separate validation process checks the solution using the benchmark's evaluation tooling.

8. **Experiment Management**: Uses a Makefile to run individual agents, launch model comparisons, validate results, and generate benchmark reports. Results are organized by model and task, allowing completed benchmark pairs to be skipped on subsequent runs.

## Key Technical Choices

### Code as the agent's action interface

Rather than relying exclusively on structured JSON tool calls, the agent expresses its actions as executable Python code.

The generated program can call the tools available in its environment, inspect their outputs, perform intermediate computations, and decide what information to retrieve next.

This creates a closed feedback loop in which execution results become observations for the next LLM iteration.

The approach is inspired by the CodeAct paradigm: executable actions are used as the interface between reasoning and the external environment.

### Execution sandbox and defense in depth

Executing code generated by an LLM introduces significant security risks. The project therefore isolates execution and applies several layers of restrictions.

- Source inspection before compilation.
- Allowlisted imports and built-ins.
- Restricted filesystem access.
- Network access restrictions.
- CPU, memory, file-size, and process-creation limits.
- Wall-clock timeouts to stop runaway execution.

The sandbox runs generated code in a separate child process and preserves output produced before a timeout when possible.

For SWE-bench, repository operations take place inside the task's Docker environment rather than directly on the host.

These restrictions reduce the impact of accidental infinite loops, resource exhaustion, and unauthorized operations. They should be understood as defense-in-depth controls rather than a guarantee that arbitrary Python execution is completely secure.

### Model Context Protocol for tool discovery

The project uses MCP to expose benchmark-specific operations through a common interface.

Each benchmark has its own tool server, and the sandbox acts as an MCP client. Discovered tools are injected into the generated Python environment as callable functions.

This design separates the agent loop from benchmark implementation details and makes it possible to extend the agent with additional tools without rewriting its core interaction logic.

The tool servers can communicate over standard input/output or through an HTTP endpoint.

### Separate agents for different programming tasks

MBPP and SWE-bench share the same core architecture but require different workflows.

**MBPP** focuses on relatively self-contained algorithmic problems. The agent generates a function and uses assertions to determine whether its implementation is correct.

**SWE-bench** requires repository-level reasoning. The agent must navigate unfamiliar source code, identify the relevant implementation, modify files, run tests, and produce a patch.

Keeping the execution loop reusable while separating benchmark-specific tools and task logic avoids duplicating the entire agent implementation.

### Configurable LLM providers and resilience

The LLM layer supports multiple OpenAI-compatible providers and configurable models.

API keys can be loaded from environment configuration, and additional keys can be used when a provider imposes rate limits. The system also records token consumption, response latency, and retries.

This architecture allows the same agent to be evaluated against different models without changing its execution engine.

It also makes provider reliability and inference cost part of the engineering evaluation rather than treating the model as an interchangeable black box.

### Explicit execution budgets

Autonomous agents can waste time and tokens repeatedly investigating an incorrect hypothesis.

The project therefore uses configurable limits on iterations, generated tokens, execution time, and other resources.

The benchmark configuration distinguishes between MBPP and SWE-bench because repository-level debugging requires a larger exploration budget than a small programming exercise.

These limits provide a practical trade-off between solution quality, execution cost, and runtime.

### Reproducible benchmarking

The project includes scripts for running a matrix of models against selected tasks, validating solutions, and generating a benchmark report.

Each model-task pair produces a separate result artifact. Validation results are cached, and completed pairs can be skipped when experiments are rerun.

Crucially, the final evaluation relies on the benchmark validator rather than trusting the agent's own claim that a task was solved.

This makes it possible to compare models on correctness, resource usage, execution time, and reliability.

## Results

The repository includes a benchmark campaign covering 11 active models, with seven SWE-bench tasks and ten MBPP tasks per model. Three additional models that left their providers' catalogues were recorded separately.

The report documents **238 model-task evaluation cells**, with validation performed through `moulinette_eval`.

### Best results in the documented campaign

| Model | SWE-bench | MBPP | Total |
|---|---:|---:|---:|
| Ministral 14B | 7/7 | 7/10 | 14/17 |
| Ministral 8B | 6/7 | 9/10 | 15/17 |
| Qwen 3.8 27B | 3/7 | 8/10 | 11/17 |
| Codestral 2508 | 2/7 | 7/10 | 9/17 |

*The table reflects the reported campaign, not a general ranking of these models or their current capabilities.*

The report selected Ministral 8B as the default model for MBPP and Ministral 14B for SWE-bench. The former achieved 15/17 validated tasks, while the latter achieved 7/7 SWE-bench tasks and 7/10 MBPP tasks in the recorded run.

### What I learned from the numbers

- **Model size alone does not determine performance.** Models with different architectures and sizes showed substantially different results across the two benchmarks.
- **Task type matters.** Some models performed well on short programming problems but struggled with repository-level debugging.
- **A plausible answer is not necessarily a correct answer.** The report records 39 claimed SWE-bench resolutions, of which 37 were confirmed by the validator.
- **Reasoning guidance can materially affect performance.** In the reported ablation study, removing the reasoning guide reduced the number of successful resolutions from 16/21 to 6/21 across three repetitions of seven SWE-bench tasks.
- **Evaluation must account for budgets.** A solution that exceeds a benchmark's resource limits may be rejected even when the proposed fix is correct.
- **Provider reliability matters.** Rate limits, retries, unavailable models, and incomplete runs can affect experimental results independently of the agent's reasoning quality.

These results demonstrate the importance of evaluating the complete agent system, including prompts, tools, execution constraints, model behavior, and validation—not just the quality of generated code.

- Treating LLM-generated code as untrusted input.
- Implementing defense-in-depth restrictions around code execution.
- Separating host resources from benchmark execution environments.
- Managing execution budgets and mitigating resource-exhaustion risks.
- Understanding the limitations of application-level Python sandboxing.

### Tool Integration & Software Engineering

- Implementing MCP clients and benchmark-specific tool servers.
- Dynamically exposing discovered tools to generated Python programs.
